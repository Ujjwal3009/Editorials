Numbers to Know for System Design Interviews

Learn about the modern hardware numbers and capacity limits you actually need to know for system design interviews in 2026.

Our industry moves fast. The hardware we build systems on evolves constantly, which means even recent textbooks can become outdated quickly. A book published just a few years ago might be teaching patterns that still make sense, but quoting numbers that are off by orders of magnitude.

One of the biggest giveaways that a candidate has book knowledge but no hands-on experience during a system design interview is when they rely on outdated hardware constraints. They do scale calculations using numbers from 2015 (or even 2020!) that dramatically underestimate what modern systems can handle. You'll hear concerns about database sizes, memory limits, and storage costs that made sense then, but would lead to significantly over-engineered systems today.

This isn't the candidate's fault – they're doing the right thing by studying. But understanding modern hardware capabilities is crucial for making good system design decisions. When to shard a database, whether to cache aggressively, how to handle large objects – these choices all depend on having an accurate sense of what today's hardware can handle. Let's look at the numbers that actually matter in 2026.

Modern Hardware Limits

Modern servers pack serious computing power. An AWS M6i.32xlarge comes with 512 GiB of memory and 128 vCPUs for general workloads. Memory-optimized instances go further: the X1e.32xlarge provides 4 TB of RAM, while the U-24tb1.metal reaches 24 TB of RAM. This shift matters because many applications that once required distributed systems can now run on a single machine.

Storage capacity has seen similar growth. Modern instances like AWS's i3en.24xlarge provide 60 TB of local SSD (solid-state drive) storage. If you need more, the D3en.12xlarge offers 336 TB of HDD (hard disk drive) storage for data-heavy workloads. Object storage like S3 is effectively unlimited, handling petabyte-scale deployments as a standard practice. The days of storage being a primary constraint are largely behind us.

Network capabilities haven't stagnated either. Within a datacenter, 25 Gbps is common for standard instances, with high-performance instances supporting 50–100 Gbps or more. Bandwidth across availability zones (AZs) within a region is limited only by instance network capacity. Latency remains predictable: sub-1ms within a single AZ, 1–2ms across AZs in the same region, and 50–150ms cross-region. This consistent performance allows for reliable distributed system design.

💡 Core Takeaway
These aren't just incremental improvements – they represent a step change in what's possible. When textbooks talk about splitting databases at 100GB or avoiding large objects in memory, they're working from outdated constraints.

Applying These Numbers in System Design Interviews

Let's look at how these numbers impact specific components and the decisions we make when designing systems in an interview.

Caching

Redis and Memcached remain the gold standards for in-memory key-value caching. A single modern Redis instance can easily handle 100,000 to 250,000 read QPS on a single core with sub-millisecond latencies (0.1ms – 0.5ms). Standard cache servers can hold 100 GB – 500 GB of RAM per box, and TBs across a Redis Cluster.

Rule of thumb: If you are caching 20% of daily active read data (Pareto 80/20 rule), a single high-memory instance can often serve the entire working set of a 10M DAU application without complex partitioning.

Databases

A single primary PostgreSQL or MySQL instance equipped with NVMe SSDs can comfortably store 4 TB to 16 TB of active relational data before you ever need to shard. A tuned SQL database can process 10,000 to 30,000 read QPS (using read replicas) and 1,000 to 5,000 ACID write transactions/sec.

For distributed NoSQL systems (like Cassandra, DynamoDB, or ScyllaDB), clusters scale linearly to handle 50,000 to 200,000+ writes/sec with single-digit millisecond latency.

Application Servers

Stateless application servers (written in Go, Java/Spring Boot, Node.js, or Rust) can easily handle 5,000 to 20,000 QPS per instance for I/O bound requests (e.g. proxying database calls, assembling JSON responses). For real-time WebSocket or Server-Sent Events (SSE) connections, a single server using epoll/kqueue can hold 50,000 to 100,000 concurrent persistent connections.

Message Queues

Apache Kafka achieves 100,000 to 500,000 messages/sec per broker by leveraging sequential disk I/O, OS page cache, and zero-copy data transfer. Managed queues like AWS SQS handle virtually unlimited horizontal throughput (and 3,000 msgs/sec for FIFO queues).

Common Mistakes In Interviews

1. Premature Sharding

Candidates frequently jump straight to database sharding as soon as they hear a dataset might reach 1 TB or 2 TB. Sharding introduces massive operational overhead: you lose foreign keys, cross-shard joins become complex, and re-sharding when keys hot-spot is painful.

⚠️ The Reality
A single modern AWS RDS PostgreSQL instance on r6i.8xlarge can hold up to 64 TB of storage with 64,000 IOPS on gp3/io2. Vertical scaling is usually the right answer until you exceed ~10 TB or write throughput exceeds ~5,000 TPS.

2. Overestimating Latency

Assuming that database reads take 50ms to 100ms. If you have proper B-tree indexes and a warm buffer pool, an indexed primary key lookup in PostgreSQL takes < 1ms from memory and < 5ms from an NVMe SSD.

3. Over-Engineering Given a High Write Throughput

Proposing Kafka pipelines, Cassandra clusters, and microservice consumers for a system that only receives 300 to 500 writes per second. A standard SQL database with write-ahead logging (WAL) easily processes thousands of writes per second on a single box.

What About Costs?

In senior and staff-level interviews, cost awareness distinguishes top candidates:

  • Compute vs Storage: CPU and RAM are expensive; S3 object storage ($0.023/GB/month) is cheap. Storing images or videos in a database is 10x more expensive than offloading to S3 with presigned URLs.
  • Egress Bandwidth: Cloud providers charge $0.05 to $0.09 per GB of outbound data egress. Delivering 1 PB of video data without a CDN (like Cloudflare or CloudFront) will incur $50,000+/month in bandwidth bills.
  • Vertical vs Horizontal: One 128-core server is often cheaper and vastly simpler to operate than a distributed cluster of 16 smaller instances.

Conclusion

Keep these numbers top of mind during your system design interviews. Grounding your estimations in real 2026 hardware limits shows practical engineering maturity and prevents you from unnecessarily over-complicating your architecture.

🎯 Final Interview Checklist
1. Always convert daily volume to QPS ($1\text{M/day} \approx 12\text{ QPS}$, $100\text{M/day} \approx 1.2\text{k QPS}$).
2. Apply peak multipliers ($2.5\text{x}$ to $3\text{x}$).
3. Calculate 80/20 RAM for caching.
4. Keep single-node limits in mind before introducing distributed sharding!
