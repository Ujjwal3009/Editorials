🖥️ 1. Modern Hardware Limits (What 1 Server Can Actually Do)

🧠

Compute & Memory

Up to 24 TB RAM

Standard instances pack massive RAM and vCPUs, rendering single-box architectures viable for millions of users.

  • AWS M6i.32xlarge: 128 vCPUs, 512 GiB RAM (General).
  • AWS X1e.32xlarge: 4 TB RAM for in-memory DBs.
  • AWS U-24tb1.metal: 24 TB RAM on bare metal.
  • Rule of thumb: You rarely need distributed caching for data under 200 GB.
💾

Storage & IOPS

60 TB NVMe / Node

Modern NVMe SSDs have demolished traditional I/O bottlenecks and disk seek penalties.

  • AWS i3en.24xlarge: 60 TB local NVMe SSD.
  • AWS D3en.12xlarge: 336 TB HDD for big data.
  • AWS EBS gp3 / io2: 16,000 to 256,000 IOPS per volume.
  • S3 Object Store: Effectively infinite petabyte scale with 99.999999999% durability.
🌐

Network & Bandwidth

25 – 100 Gbps

Datacenter network backplanes support staggering throughput with predictable latencies.

  • Standard Instances: 25 Gbps baseline network bandwidth.
  • High-Perf Instances: 50 to 100+ Gbps dedicated throughput.
  • Intra-AZ Latency: Sub-1 millisecond (<0.5ms).
  • Cross-AZ (Same Region): 1 – 2 milliseconds.

🏗️ 2. Core System Component Capacities

⚡

Caching Tier (Redis / Memcached)

  • Throughput: 100,000 – 250,000 QPS on a single modern Redis core with pipelining.
  • Latency: 0.1 ms – 0.5 ms for in-memory lookups.
  • Storage: 100 GB – 500 GB per single instance; TBs across Redis Cluster.
  • Interview Rule: Use for sub-millisecond hot key reads and 80/20 Pareto caching.
🗄️

Databases (SQL & NoSQL)

  • RDBMS (PostgreSQL / MySQL): 4 TB – 16 TB per node before sharding.
  • SQL Reads: 10,000 – 30,000 QPS on tuned primary with read replicas.
  • SQL Writes: 1,000 – 5,000 TPS on a single instance (ACID logging).
  • NoSQL (Cassandra / DynamoDB / ScyllaDB): 50,000 – 200,000+ writes/sec distributed.
🚀

Application Servers (Go, Java, Node, Rust)

  • Throughput: 5,000 – 20,000 QPS per instance for I/O bound APIs (Async/Epoll).
  • CPU Heavy Tasks: 500 – 2,000 QPS (JWT signing, image rendering, encryption).
  • Concurrent Connections: 50,000 – 100,000 open WebSockets/SSE connections per box.
📬

Message Queues & Event Streaming

  • Apache Kafka: 100,000 – 500,000 msgs/sec per broker (Zero-copy OS page cache).
  • RabbitMQ: 10,000 – 40,000 msgs/sec (Complex routing, AMQP).
  • AWS SQS: Virtually unlimited throughput with standard queues (3,000 msgs/sec for FIFO).

⚠️ 6. Top 5 System Design Interview Mistakes

❌ Mistake 1: Premature Sharding
Many candidates propose sharding when a database only has 500 GB or 2 TB of data. A single modern RDS PostgreSQL or MySQL instance can comfortably handle up to 16 TB – 64 TB with automated read replicas and NVMe SSDs (gp3 / io2). Sharding introduces cross-shard joins, distributed transactions, and rebalancing complexity that is rarely needed at moderate scale.
❌ Mistake 2: Overestimating Latency
Assuming that database reads take 50–100ms. An indexed B-tree point lookup in memory/buffer cache takes < 1ms, and reading from an NVMe SSD takes < 5ms. Overestimating latency leads to unnecessary caching layers.
❌ Mistake 3: Over-Engineering for Moderate Write Throughput
Introducing Kafka, Cassandra, and microservice pipelines for 500 writes/sec. A single standard PostgreSQL instance easily processes 2,000 to 5,000 ACID writes/sec with connection pooling.
❌ Mistake 4: Caching Everything Blindly
Adding Redis for data with a low read-to-write ratio (< 3:1) or volatile data. Caching adds cache invalidation complexity and race conditions without performance benefits if the cache hit rate is below 80%.
❌ Mistake 5: Ignoring Network Egress Bandwidth
Calculating storage accurately but forgetting that delivering 50,000 simultaneous video streams at 2 Mbps requires 100 Gbps of sustained outbound bandwidth. Always calculate egress for media-heavy systems!
